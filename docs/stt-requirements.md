# STT 공급자 요건

특정 공급자를 확정하지 않는다. 대신 **우리가 요구하는 것**을 적어두고, 이 목록으로 공급자 후보를 평가한다.

Soniox로 한 차례 실측했으나 채택하지 않는다. 그 실측의 성과는 공급자 선택이 아니라 **아래 요건 목록을 알게 된 것**이다.

다만 만들려면 무엇이든 붙어야 한다. **CLOVA Speech를 기본으로, gpt-4o-transcribe를 비교군으로 둘 다 붙인다**(아래 *공급자 후보* 참조). 채택이 아니라 자리 채우기이며, **STT는 인터페이스 뒤에 둔다** — 표면은 [seams.md](./seams.md)의 ⓵가 정본이다. 인터페이스가 필수 요건 1~4를 반영한 모양이어야 나중에 교체가 싸다.

## 필수

| | 요건 | 왜 |
|---|---|---|
| 1 | **async(파일) 전사** | 실시간 처리를 하지 않기로 확정. 회의 종료 후 배치 |
| 2 | **컨텍스트/용어 주입** | 아래 별도 항목 참조 |
| 3 | **화자 분리** (단일 혼합 스트림) | 의견의 출처를 남기기 위해. 대면 단일 마이크에서 동작해야 함. **v0.5에서는 선택** — 화자 라벨의 소비자가 없고, 필요해지면 보존된 오디오를 재처리해 복구한다 |
| 4 | **단어 또는 구간 타임스탬프** | 아래 별도 항목 참조 |
| 5 | 한국어 정확도 | — |
| 6 | 장시간 오디오 (1~2시간) | — |

## 선택

| | 요건 | 왜 |
|---|---|---|
| 7 | 음성 등록 기반 화자 식별 | 있으면 회의마다 하는 이름 매핑을 대체할 수 있다 |

## 2번(컨텍스트 주입)이 정확도 벤치마크보다 우선하는 이유

실측에서 나온 문제는 **특정 용어(제품명·전문용어)를 한 번 잘못 인식하면 회의 내내 같은 식으로 계속 틀리는 것**이었다. 그리고 컨텍스트 파라미터를 넣지 않은 상태였다. 넣지 않은 이유는 **"매번 우리 맥락에 맞춰 써서 넣는 게 번거로워서"** 였다.

그 번거로움을 없애는 것이 이 제품의 존재 이유다. 이슈 로그는 회의를 하면 자동으로 쌓이고, **그것이 곧 다음 회의의 컨텍스트다.**

```
회의 → 이슈 로그 → 다음 회의의 STT 컨텍스트 → 더 나은 회의록 → 더 나은 이슈 로그
```

이 설계에서 **로그가 쌓인 보상이 가장 빨리 돌아오는 지점**이다(회의 2회차부터). 컨텍스트 주입 기능이 없는 공급자를 고르면 이 고리가 통째로 사라진다.

**평가 시 확인할 것:**
- 자유 텍스트를 받는가, 용어 목록만 받는가 (요약 문서를 통째로 넣을 수 있어야 좋다)
- **토큰/문자 한도** — 이슈 목록을 얼마나 넣을 수 있는지를 결정한다. 목록의 크기는 [mvp-scope.md](./mvp-scope.md)의 v2 항목이 정본이다
- 한도 초과 시 무엇을 버릴지는 상태로 정한다: 무효를 먼저 빼고, 오래전에 결정된 것부터 요약한다. MCP 목록의 "전량·시간으로 자르지 않음" 원칙과는 별개다 — 여기는 공급자 한도가 있는 자리다

### 컨텍스트에 들어가는 것은 네 가지다

| | 소스 | 성격 | 갱신 |
|---|---|---|---|
| 1 | **참가자 명단** | 팀원 이름 | 거의 고정 |
| 2 | **용어집** | 팀 고유명사·전문용어 | 사람이 확인하며 천천히 자람 |
| 3 | **미확인 후보와 쟁점** | 이번 회의에서 다룰 질문들 | 회의마다 |
| 4 | **이슈 목록** | 결정과 쟁점의 한 줄 요약 | 회의마다 자동 |

같은 한도를 나눠 쓴다. 한도가 찰 때의 우선순위는 실측으로 정하되, **출발점은 위 순서**다. 1은 몇 단어뿐이고 3도 몇 줄뿐이라 사실상 공짜다. 밀려나는 건 늘 4다.

#### 다만 실제 API 앞에서 이 그림은 반쯤 무너진다

컨텍스트 주입에 두 형태가 있고, 대부분의 공급자가 **키워드 목록형**이다.

| 형태 | 공급자 | 넣을 수 있는 것 |
|---|---|---|
| **자유 텍스트** | Whisper(224토큰), gpt-4o-transcribe | 문장. 즉 소스 1~4 전부 |
| **키워드 목록** | CLOVA(1,000개), ElevenLabs(1,000×50자), AssemblyAI(1,000), Deepgram(500토큰) | 단어·짧은 구. **소스 1·2만** |

위의 *"리버스 프록시 — Caddy / nginx 한 줄이 올라가면 그 영역 어휘가 통째로 살아난다"* 는 **키워드형에서는 그 한 줄을 못 넣는다.** CLOVA 문서가 명시적으로 경고한다 — *"여러 단어들이 조합된 구문일 경우 해당 구문이 아니면 부스팅의 영향을 받기 어려움."*

**완화책은 이미 시스템 안에 있다.** 이슈 제목과 답의 고유명사는 추출이 **용어 후보로 이미 뽑고 있다**([CONTEXT.md](../CONTEXT.md)의 용어집 항목). 키워드형에서는 **소스 2가 소스 3·4의 역할을 상당 부분 흡수한다.**

그래서 우선순위는 그대로 두되, 기대치를 고쳐 적는다:

```
자유 텍스트형  →  네 소스가 실제로 대등하게 한도를 나눈다
키워드 목록형  →  소스 2만 제대로 들어간다. 3·4는 용어집을 통해 우회한다
```

**공급자 선택 기준도 여기서 바뀐다** — 컨텍스트 주입은 있고 없고가 아니라 **형태와 한도**로 봐야 한다.

### 3번이 없으면 새 영역은 원리적으로 안 덮인다

용어집과 이슈 목록은 **과거에서만 온다.** 그래서 처음 나오는 얘기는 구조적으로 컨텍스트가 0이고, 회의에서 가장 중요한 건 대개 처음 나오는 얘기다.

**3번만 미래를 가리킨다.** 배포를 처음 다루는 회의에서 "리버스 프록시 — Caddy / nginx"가 한 줄 올라와 있으면 그 영역의 용어가 통째로 살아난다. 인접 용어까지 함께 올라오므로 단어 목록이 아니라 **영역 힌트**로도 작동한다.

**1회차에 존재하는 것은 1번과 3번뿐이다.** 후보 등록은 첫 회의 전에도 할 수 있고, 참가자 명단은 처음부터 알고 있다. 나머지 둘은 회의를 한 번 해야 생긴다.

이 목록은 회의 절차 2번에서 어차피 화면에 띄우는 것이므로 추가 비용이 없다([mvp-scope.md](./mvp-scope.md)).

### 대가 — 주입한 어휘 쪽으로 끌려간다

컨텍스트 주입이 작동하는 메커니즘은 거꾸로도 돈다. 목록에 `Caddy`가 있으면 "응답 **캐시**를 걸어두면"이 "응답 **Caddy**를 걸어두면"으로 나올 수 있다.

주입하는 어휘가 많을수록 이 오류도 늘어난다. 새 영역 용어를 여럿 복구하는 이득에 비하면 작을 것으로 보지만, 공급자 평가에서 이 방향도 같이 잰다. 오디오를 보존하므로 의심되면 재전사로 확인할 수 있다.

## 4번(타임스탬프)을 놓치기 쉬운 이유

근거 구조가 여기 걸려 있다. 타임스탬프가 없으면 "이 결정의 근거는 회의록 어느 지점"을 가리킬 수 없고, 이슈에서 **회의록 구간**으로 내려가는 경로가 성립하지 않는다.

## 화자 이름 매핑

화자 분리는 보통 `Speaker 1`, `Speaker 2` 같은 익명 라벨만 준다. 세션마다 번호가 달라지므로 회의마다 매핑이 필요하다.

**채택안:** 회의 시작 라운드에서 각자 **이름을 말하고** 지난 회의 이후 한 일을 보고한다. 회의록에 이름이 들어가므로 발화 순서와 무관하게 매핑할 수 있다. 이미 하기로 한 일에 이름 한 단어를 붙이는 것이라 추가 비용이 없다.

**참가자 명단은 1회차부터 컨텍스트에 넣는다.** 이름은 용어집과 달리 회의록에서 배울 필요가 없다 — 팀 명단은 처음부터 알고 있다. 이걸 놓치면 이름이 깨질 확률이 가장 높은 회차가 하필 1회차가 된다.

**폴백:** 확인 화면에서 사람이 직접 지정(회의당 6클릭). 발화가 겹쳐 이름을 놓치는 경우가 실제로 생긴다.

## 화자 정확도에 대한 기대치

대면·단일 마이크·6명·발화 겹침은 화자 분리에 가장 불리한 조건이다. 실제 미가공 오디오의 화자 오류율은 문헌상 10~18% 수준이며, 설정으로 없앨 수 없다.

**이 오류를 감당할 수 있게 설계돼 있다:**

- 화자는 결정에 붙지 않는다. **의견에만** 붙는다
- 의견은 목록과 확인 화면 요약에 나오지 않고 상세에만 들어간다
- 회의 직후 확인 화면에서 참석자가 함께 보므로 오귀속이 드러날 자리가 있다

정확한 화자 기록으로는 실패하는 수준이지만, **"누가 이 걱정을 했었지"를 나중에 되짚는 용도로는 충분하다.**

**가장 싼 개선책은 소프트웨어가 아니다.** 테이블 중앙의 회의용 마이크 하나가 노트북 내장 마이크보다 전사 품질과 화자 분리를 동시에 크게 개선한다.

## 공급자 후보

### 한국어 정확도 — CER

`회의` 컬럼이 우리 조건에 가장 가깝다. 낮을수록 좋다.

| API | Avg CER | **회의** |
|---|---|---|
| Return Zero (RTZR) | 5.91 | 6.74 |
| RTZR Whisper | 6.59 | 8.33 |
| **Naver CLOVA Speech** | **7.52** | **7.63** |
| ETRI | 10.19 | 10.56 |
| Azure batch STT | 10.88 | 9.95 |
| AWS Transcribe | 11.11 | 9.65 |
| OpenAI Whisper | 11.39 | 10.16 |
| Google API v2 | 11.50 | 11.62 |
| Gemini 2.0 Flash | 16.58 | 11.98 |
| Deepgram nova-2 | 21.02 | 17.8 |

출처: [rtzr/Awesome-Korean-Speech-Recognition](https://github.com/rtzr/Awesome-Korean-Speech-Recognition)

**이 표를 그대로 믿으면 안 된다.** RTZR이 만든 벤치마크고 RTZR이 1등이다. 그리고 **gpt-4o-transcribe, ElevenLabs Scribe v2, AssemblyAI Universal-3.5, Deepgram nova-3, Speechmatics가 아예 빠져 있다.**

읽을 수 있는 신호는 하나다 — **한국어에서 국산과 글로벌 범용의 격차가 크고, 그 차이는 대부분 고유명사와 조사에서 난다.** 정확히 우리가 아픈 자리다.

### 선택

**기본: CLOVA Speech. 비교군: gpt-4o-transcribe.**

CLOVA를 기본으로 두는 이유:

- 회의 CER 7.63으로 사실상 최상위 (1·2위는 벤치마크 제작사 자기 모델)
- **boostings 1,000개** — 용어집이 아무리 자라도 한도에 안 찬다
- **한국어와 영어를 둘 다 받는다.** 우리 회의 용어가 영어 반 한글 반이라 이게 중요하다. RTZR은 CER 1위지만 기본 모델이 한글 키워드 위주다
- 화자 분리에 min/max 화자 수를 지정할 수 있다 — 6명인 걸 알고 있으니 유리하다
- 동기 + 비동기 둘 다, 구간 + 단어 타임스탬프

gpt-4o-transcribe를 나란히 붙이는 이유:

**자유 텍스트 컨텍스트를 쓸 수 있는 유일한 후보**다. 그러면 이 문서의 핵심 주장 — *컨텍스트 주입이 정확도 벤치마크보다 우선한다* — 을 실제로 시험할 수 있다.

다만 **비대칭이 있다.** 자유 텍스트의 이득은 회차가 쌓여야 나오는데(용어집·이슈 목록이 생겨야 한다), 기본 정확도의 손해는 1회차부터 전액 발생한다. 그리고 1회차 회의록이 용어집의 씨앗이다. **그래서 1회차 기본은 CLOVA로 간다.** 오디오를 보존하므로 같은 녹음으로 나중에 비교할 수 있어 손해가 없다.

**확인할 것**: gpt-4o-transcribe-diarize는 컨텍스트 창 16k, 최대 출력 2k, 청크 한도 1400초다. 오디오와 프롬프트가 같은 16k를 나눠 쓰는 구조로 보이는데, 그렇다면 "자유 텍스트라 컨텍스트가 넉넉하다"는 전제가 흔들린다. 짧은 파일에 긴 프롬프트를 넣어보면 바로 나온다.

### 나중 후보

| 언제 | 무엇 |
|---|---|
| 화자가 중요해지면 | ElevenLabs Scribe v2 (화자 라벨 98%, keyterm 1,000×50자) / AssemblyAI Universal-3.5 Pro |
| 실시간이 필요해지면 | Deepgram Nova-3 — 다만 한국어 CER이 목록에서 가장 나쁘다 |

Speechmatics는 한국어를 잘 하지만 엔터프라이즈 협의 가격이라 6인 팀에 안 맞는다.

### 비용은 결정 요소가 아니다

2시간 회의 하나 기준으로 전사 $0.5~1.5, 추출 $0.15~0.35다. 주 1회면 월 $5 남짓이다. **품질만 보고 고르면 된다.**

### 추출 LLM

**Opus 5로 시작해 Sonnet 5로 내려본다.**

순서 0번의 판정이 *"이슈 모델이 서는가"* 이고, 실패하면 이슈 모델 자체를 재검토한다([mvp-scope.md](./mvp-scope.md)). 약한 모델로 재서 실패하면 **모델 탓인지 설계 탓인지 구분이 안 된다.** 설계 전체가 걸린 판정을 월 $1 아끼려고 오염시킬 이유가 없다.

```
Opus 5로 재서 실패  →  설계 문제. 이슈 모델을 재검토한다
Opus 5로 재서 성공  →  Sonnet 5로 내려보고, 품질이 유지되면 거기 머문다
```

**위에서 아래로 내려온다.** 아래에서 올라가면 "이 정도면 된 건가"를 판정할 기준이 없다.

배치 API는 최대 24시간 지연이라 쓸 수 없다 — *회의 직후 그 자리에서*가 이 제품의 핵심이다. 프롬프트 캐싱은 쓰되, 회의록 본문은 매번 다르므로 절감폭은 지시문 부분에 한정된다.

## 공급자 평가 절차

이미 확보한 회의 녹음 파일로 공급자 후보를 같은 조건에서 비교한다.

1. 컨텍스트 없이 전사 → 기본 품질
2. **팀 용어를 컨텍스트에 넣고 전사** → 용어 고착이 사라지는지
3. 2번 결과에서 **주입한 어휘로 잘못 끌려간 곳**을 센다 → 위 *대가* 항목
4. 화자 분리 결과를 사람이 눈으로 검증

2번이 이 평가의 핵심이고, 3번은 2번의 이득에서 빼야 할 값이다.
