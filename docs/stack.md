# 스택

C층이다. 바꾸는 비용이 낮으므로 지금 고르되 붙들지 않는다.

```
Java 25 · Spring Boot 4.1 · jOOQ + Flyway · PostgreSQL
React 19 · TypeScript · Vite 7 · TanStack Query · Tailwind 4 · shadcn/ui   (Node 24)

테스트   JUnit 5 + AssertJ + Testcontainers   |   Vitest + RTL + MSW
실행     docker-compose (로컬)                |   배포는 신호가 오면
```

## 왜 이 스택인가

**이 프로젝트의 실패 모드는 기술적 어려움이 아니라 "안 만들어지는 것"이다.** 범위를 v0.5까지 깎아낸 것도 그래서다([ADR 0004](./adr/0004-scope-by-substitute.md)). 새 언어를 배우는 비용은 그 위험을 키운다.

팀이 직전 프로젝트를 Spring Boot + React로 배포까지 끌고 갔다. 추측이 아니라 이력이므로, 뒤집으려면 그보다 강한 이유가 필요한데 이 프로젝트의 제약 어디에도 그런 게 없다.

## 가장 중요한 건 프레임워크가 아니라 이 경계다

```
domain/          ← 순수 Java. 프레임워크 없음
  ports/            SttPort, ExtractPort   (seams.md)
  상태 기계, 확인(승격), 컨텍스트 조립·우선순위
adapters/
  stt/              clova / openai / replay / simulator
  extract/          llm / fake
app/             ← Spring Boot. HTTP, 잡 실행, 저장, (v2) MCP
web/             ← React
sim/             ← 회차 시뮬레이터. domain + fake 어댑터, Spring 부팅 없음
```

**`sim/`이 프레임워크 없이 돌아야 한다.** 회차 시뮬레이터가 개발 루프의 중심인데 매번 Spring 컨텍스트를 띄우면 그 루프가 느려진다([ADR 0005](./adr/0005-simulate-rounds-not-calls.md)). 이 경계는 스택을 바꿔도 지켜야 하는 것이다.

## 개별 결정

| | | 왜 |
|---|---|---|
| **jOOQ + Flyway** | JPA는 안 쓴다 | 스키마가 정본이고 코드가 파생물이라, A층 빈칸을 메우며 스키마가 움직여도 컴파일 에러로 잡힌다. 둘 다 쓰면 어느 쪽이 정본인지 흐려진다 |
| **PostgreSQL** | SQLite에서 바꿈 | 아래 |
| **비동기 잡** | 인프로세스 스레드풀 + 잡 테이블 | 6명·주 1회·동시 잡 1개. 큐 미들웨어는 배포만 무겁게 한다. 청크 병렬은 이 안에서 |
| **잡 유실 복구** | 재처리 | 오디오가 보존되므로 별도 장치가 필요 없다 |
| **진행 상태** | 폴링 | 잡 하나, 사용자 6명 |
| **오디오·원본응답** | 파일시스템, 경로만 DB | 픽스처로 내보내기 쉽다 — 골든 파일이 여기서 나온다 |
| **프론트 서빙** | Vite 빌드 → Spring static | 서버 하나, CORS 없음 |
| **MCP (v2)** | 같은 앱 안, HTTP/SSE | 별도 프로세스가 같은 DB를 여는 것보다 단순하고, **MCP가 DB를 직접 만지면 [ADR 0002](./adr/0002-ai-cannot-decide-issues.md)의 경계가 우회된다.** 도메인 API를 통해야 한다 |

## PostgreSQL로 바꾼 이유

[mvp-scope.md](./mvp-scope.md)는 원래 SQLite였다. 근거를 따져보니 Postgres가 낫다.

| | SQLite | PostgreSQL |
|---|---|---|
| **jOOQ 코드 생성** | 동적 타입이라 컬럼 타입이 뭉개진다 | 강타입 → 생성 코드가 정확 |
| **스키마 변경** | `ALTER TABLE` 제한적. 컬럼 삭제·변경이 **테이블 재생성** | 자유롭다 |
| 원본 응답·추출 결과 | JSON1은 약하다 | **jsonb** |
| 타임스탬프 | 전용 타입 없음 | 있다 |
| 팀 숙련도 | 새 조합 | **직전 프로젝트에서 씀** |

**결정적인 건 두 번째 줄이다.** A층 빈칸을 메우며 v0.5를 만드는 동안 스키마가 계속 움직이는데, SQLite의 `ALTER TABLE` 제약이 정확히 그 시기에 아프다.

SQLite의 유일한 큰 장점이던 테스트 격리는 **Testcontainers**로 대체된다. 컨테이너를 한 번 띄우고 회차마다 트랜잭션 롤백이나 스키마 재생성으로 격리하면 회차 시뮬레이터는 여전히 몇 초에 돈다.

## 프론트엔드 기준

*AI와 커뮤니케이션이 원활할 것*과 *테스트 용이성*으로 골랐다. 화면 자체의 기준은 하나 더 있다 — **미감이 아니라 사용성이다.** 확인 화면은 회의 직후 6명이 프로젝터 앞에서 한 장씩 넘기는 자리고([mvp-scope.md](./mvp-scope.md)의 `확인 화면`), 거기서 값을 만드는 건 예쁜 것이 아니라 손이 멎지 않는 것이다.

- **TypeScript** — AI가 자기 실수를 타입으로 잡는다. 이 기준에서 가장 큰 한 방
- **React 19** — 학습 데이터가 압도적이다. 이 기준에선 그게 곧 정확도다
- **TanStack Query** — 전사 대기 화면이 *"5초마다 잡 상태를 폴링하다가 완료되면 결과를 가져온다"* 인데 훅 하나로 선언된다. 직접 짜면 `useEffect` + `setInterval` + 정리 로직이 되고, **AI가 가장 자주 틀리는 코드가 정확히 그 조합**이다
- **Tailwind 4** — 스타일이 마크업 옆에 붙어 AI가 파일 두 개를 오가지 않는다. 별도 CSS 파일로 두면 클래스 이름 규약이 **매번 새로 생긴다**. 규약이 없는 게 문제가 아니라 매번 달라지는 게 문제다
- **shadcn/ui** — 컴포넌트 소스가 `web/` 안으로 복사돼 들어온다. `node_modules` 안의 컴포넌트는 AI가 읽지도 고치지도 못하지만 복사된 소스는 그냥 우리 코드다. 버전 업그레이드라는 사건이 없는 것도 *지금 고르되 붙들지 않는다*는 C층 원칙과 맞는다
- **MSW** — API 목이 네트워크 레벨에 걸려서 컴포넌트가 테스트를 위해 모양을 바꾸지 않는다. `sim/`이 내보내는 응답을 그대로 프론트 픽스처로 쓸 수 있다
- **전역 상태 라이브러리 없음** — 이 앱의 상태는 전부 서버 상태다. 층이 하나 줄면 AI가 헷갈릴 자리도 하나 준다

**shadcn/ui를 고른 진짜 이유는 그 아래 Radix다.** 확인 화면은 한 장 15줄로 장을 넘기는 리듬인데, 마우스로 스물몇 번 클릭하는 화면이면 그 리듬이 늘어진다 — 키보드로 넘어가야 한다. 포커스 이동·키 핸들링·`role`과 `aria`는 직접 짜면 **AI가 가장 자주 틀리면서 틀려도 화면상으로는 멀쩡해 보이는** 종류의 코드다. Radix가 그걸 프리미티브로 준다. 덤으로 테스트 기준에도 걸린다 — `role`이 제대로 붙어 있으면 RTL의 `getByRole`이 그대로 먹고, 테스트를 위해 `data-testid`를 심을 일이 없다.

**MUI·Ant 같은 통짜 라이브러리는 뺐다.** 화면 넷에 사용자 여섯인데 테마 시스템이 딸려 오고, 고쳐야 할 코드가 `node_modules` 안에 있어 *AI와 커뮤니케이션이 원활할 것*에 정면으로 어긋난다.

**Svelte 5는 뺐다.** 코드가 더 간결하지만 runes API가 새로워 학습 데이터가 얇다. *AI와 커뮤니케이션이 원활할 것*이라는 기준에 정면으로 어긋나서 장점이 상쇄된다.

**디자인 시스템·브랜딩·다크 모드는 만들지 않는다.** 노트북 한 대를 프로젝터에 물리는 화면이다. shadcn 기본값을 그대로 쓰고, 손대는 것은 밀도(한 장 15줄)와 키보드 동선뿐이다.

## 직전 프로젝트에서 안 가져오는 것

| | 왜 |
|---|---|
| JPA | 위 참조 |
| 메시지 큐(AMQP) | 잡 하나. 큐가 필요할 만큼 안 쌓인다 |
| Spring Security | 인증이 범위 밖. 사용자 식별도 없다([ADR 0004](./adr/0004-scope-by-substitute.md)) |
| WebSocket | 폴링으로 충분하다 |
| Playwright | 화면 넷, 사용자 여섯. 손으로 도는 게 싸다. 통합은 회차 시뮬레이터가 한다 |

## 배포는 지금 정하지 않는다

**1~3회차는 서버가 아예 필요 없다.** 대면 회의라 노트북 하나를 프로젝터에 물리면 6명이 같은 화면을 본다. 확인 화면의 가치는 *같은 문장을 같은 시각에 보는 것*이지 각자 접속하는 게 아니다.

**안전 조건**: `docker-compose`로 로컬 실행이 되게 해두면 서버 이전이 거의 공짜가 된다. 이게 "지금 안 정하는 것"을 안전하게 만든다.

**서버가 필요해지는 신호**

| |
|---|
| 회의 사이에 후보를 등록하고 싶어질 때 |
| 결석자가 생겨 나중에 읽어야 할 때 |
| 노트북 주인이 없는 회의가 생길 때 |

그전까지 클라우드·리전·인스턴스는 정하지 않는다. 용량은 문제가 아니다 — 2시간 회의 오디오가 압축해서 ~50MB, 주 1회면 연 2.5GB다.

- **확인 화면의 키보드 동선** — 어떤 키로 O/X를 넘기고 포커스가 다음 줄로 어떻게 가는지, 잘못 누른 것을 어떻게 되돌리는지. 화면을 처음 붙이는 티켓에서 정한다
- 서버 위치
