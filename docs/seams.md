# Seam — 갈아끼울 수 있어야 하는 경계

[mvp-scope.md](./mvp-scope.md)가 격리 대상으로 지목한 두 곳(**STT**, **추출**)에 하나가 더 붙는다 — **녹음 경계**. 지연을 어디서 숨길지가 인터페이스의 입력 단위를 정하기 때문이다.

```
오디오 ─┬─→ [컨텍스트 조립] ─→ ⓵STT ─→ 회의록 ─→ ⓶추출 ─→ 저장 ─→ 확인 ─┐
        │                                                                    │
        └─ ⓷녹음 경계·트리거                    (다음 회의) ←───────────────┘
```

---

## ⓵ STT

### 무엇이 경계를 넘는가

| 어댑터가 아는 것 | 도메인이 아는 것 |
|---|---|
| 공급자 API, 인증, 폴링 | **무엇을** 컨텍스트에 넣을지 |
| **한도**와 그 단위(토큰/문자/개수) | **어떤 순서로** 중요한지 |
| 컨텍스트 형태(자유 텍스트냐 목록이냐) | 무효 제외, 회의·이슈·용어집 개념 |
| 화자 라벨·타임스탬프 정규화, 청킹 | 회의록이 근거로 쓰인다는 것 |
| 재시도, 레이트리밋 | |

**한도는 어댑터, 우선순위는 도메인.** 이 둘이 다른 쪽에 있는 게 이 seam의 유일한 어려움이다.

### 한도 문제

도메인이 직접 재단하려면 "이걸 텍스트로 만들면 몇 자인지"를 알아야 하고, 그건 어댑터의 변환 규칙이다. 그 순간 공급자 지식이 도메인으로 샌다.

→ **도메인이 우선순위 순으로 정렬된 전량을 넘기고, 어댑터가 자기 한도까지 앞에서부터 채운다.**

```
도메인:  "이 순서로 중요하다"  →  [명단…] [용어…] [후보·쟁점…] [이슈…]
어댑터:  "내 한도는 여기까지"  →  ────────────────────────┤ 잘림
```

도메인은 형태를 모르고, 어댑터는 의미를 모른다.

**어댑터는 무엇이 잘렸는지 돌려준다.** [mvp-scope.md](./mvp-scope.md)의 열린 항목 *"컨텍스트 한도가 찰 때의 우선순위 — 실측으로 확정"* 은 잘린 걸 관측할 수 없으면 원리적으로 못 잰다. 조용한 절단은 "다 넣었다"로 읽힌다.

**한도를 조회하는 연산은 두지 않는다.** 도메인이 그 값으로 분기하면 그게 공급자 지식이 새는 통로다. 사후에 `잘린컨텍스트`를 보는 쪽이 단순하고 관측도 정확하다.

**요약은 넣지 않는다.** [stt-requirements.md](./stt-requirements.md)가 *"오래전에 결정된 것부터 요약한다"* 고 했지만 이슈 수십 건은 한도에 안 찬다. 잘라내기만 하고, 실제로 차기 시작하면 그때 붙인다.

### 표면

```
전사요청(오디오, 컨텍스트항목[])  → 작업ID     requestTranscription(Audio, List<ContextItem>) → JobId
작업상태(작업ID)                  → 대기중 | 처리중(완료청크/전체) | 완료 | 실패
                                              jobStatus(JobId) → Waiting | Running(doneChunks, totalChunks) | Done | Failed
결과(작업ID)                      → 회의록 + 반영된컨텍스트 + 잘린컨텍스트 + 원본응답[]
                                              result(JobId) → TranscriptionResult(transcript, appliedContext, droppedContext, rawResponses)

컨텍스트항목  { 종류: 명단|용어|후보쟁점|이슈, 표기, 뜻? }
              ContextItem { ContextKind: ROSTER|TERM|OPEN_CANDIDATE|ISSUE, spelling, meaning? }
발화구간      { 화자라벨?, 시작초, 끝초, 텍스트 }
              Utterance { speakerLabel?, startSec, endSec, text }
```

**왼쪽은 팀이 쓰는 말, 오른쪽은 코드에 서는 이름이다.** 왼쪽을 그대로 식별자로 옮기지 않는다 ([ADR 0006](./adr/0006-english-identifiers-korean-vocabulary.md)).

**`종류`가 필요한 이유** — CLOVA의 `boostings`, Deepgram의 `keyterm`, ElevenLabs의 keyterm은 **단어 목록**이라 이슈 한 줄을 통째로 못 넣는다. 어댑터가 `종류 == 용어|명단`만 뽑아 쓰고 나머지를 버릴 수 있어야 한다. 자유 텍스트형은 다 이어붙인다. ([stt-requirements.md](./stt-requirements.md)의 *컨텍스트 형태* 참조)

**`뜻`은 optional로 넘기고 쓸지는 어댑터가 정한다.** STT에 뜻이 무가치하다는 판단은 대체로 맞지만, 자유 텍스트를 받는 공급자에겐 설명 한 줄이 문맥으로 작동할 수 있다. 이건 공급자 특성이다.

**`화자라벨`은 optional이다.** Whisper 계열은 화자 분리를 하지 않는다. 필수로 두면 어댑터가 거짓 라벨을 채우게 된다.

### 결정 셋

**비동기를 감추지 않는다.** 긴 호출을 `await` 하나로 감싸면 대기 화면에 아무것도 못 띄운다. 진행률은 청크 수로 센다 — 공급자가 주는 게 아니라 어댑터가 아는 값이다.

**타임스탬프는 구간으로 통일한다.** 요건 4는 "단어 또는 구간"인데, 근거 구조가 요구하는 건 "이 결정의 근거는 회의록 어느 지점"이라 구간이면 충분하다. 단어 단위를 주는 공급자면 어댑터가 묶는다.

**공급자 원본 응답을 저장한다.** 어댑터 버그로 파싱이 틀렸을 때 재처리할 수 있고, 공급자 비교 시 같은 응답을 다시 해석할 수 있다. 그리고 그대로 테스트 픽스처가 된다([ADR 0005](./adr/0005-simulate-rounds-not-calls.md)).

**실시간은 대비하지 않는다.** 스트리밍은 인터페이스를 풀에서 푸시로 바꾼다. 오프라인 대면 회의만 다루는 지금 자리를 비워두는 건 추측이고, [ADR 0003](./adr/0003-no-external-task-tool.md)이 외부 도구에 쓴 논리가 그대로 적용된다. 필요해지면 두 번째 인터페이스를 만든다.

## ⓶ 추출

### 출력 스키마는 도메인이 소유한다

```
추출결과 {
  메타        { 모델명, 프롬프트버전, 프롬프트해시, 토큰수? { 입력, 출력, 캐시적중 } }
  이슈후보[]  { 로컬키, 질문, 상태(쟁점|결정), 답?, 미결정사유?, 근거구간[] }
  의견[]      { 이슈후보참조?, 화자라벨?, 내용, 근거구간 }
  할일[]      { 이슈후보참조?, 내용, 담당자표기?, 근거구간 }
  용어후보[]  { 표기, 뜻?, 근거구간[] }
}
```

*프롬프트·모델 교체가 스키마를 건드리지 않아야 한다*([mvp-scope.md](./mvp-scope.md))를 지키려면 스키마가 도메인 것이어야 한다. 반대로 하면 프롬프트를 고칠 때마다 마이그레이션이 붙는다.

할 일·의견은 v0.5에 화면이 없지만 **뽑아서 저장한다.** 호출 비용이 같고 나중에 화면 붙일 때 데이터가 이미 있다.

**`이슈후보참조`는 optional이다.** 어느 이슈에도 안 붙는 의견이 실제로 나온다 — 배경 설명, 반대만 하고 질문이 안 선 발언. 필수로 두면 추출기가 버리거나(누락) 이슈 후보를 지어내는데(과잉분할), 둘 다 이 경계가 피하려는 것이다. 화면이 없으니 무소속으로 담는 비용이 0이다.

**`토큰수`는 통째로 optional이다.** 마커 대본 추출기는 모델을 안 부른다. `0`을 채우면 *측정되지 않았다*가 *0이었다*로 읽히고, 여러 벌을 나란히 놓을 때 그 벌이 제일 싼 것으로 찍힌다. `화자라벨?`에 쓴 논리와 같다 — 필수로 두면 어댑터가 거짓 값을 채운다. 입력·출력을 나누는 것은 프롬프트 캐싱 절감이 입력에만 걸리기 때문이다.

`무효`는 추출이 제안하지 않는다. 회의록에서 판단할 신호가 거의 없고 사람이 고친다.

**추출 결과는 이슈가 아니다.** 후보는 추적 대상이 아니므로([CONTEXT.md](../CONTEXT.md)) 따로 저장되고, 확인이 이슈로 승격시킨다. 같은 레코드로 두면 확인 전 데이터가 이슈 목록과 컨텍스트로 샌다.

### 근거 구간은 번호로 참조한다

LLM에게 타임스탬프를 뱉게 하면 틀린다. 회의록에 구간 번호를 붙여 넣고 출력에 번호를 담게 한 뒤, 어댑터가 번호 → 타임스탬프로 되돌린다.

```
[17] 화자2: 리버스 프록시는 Caddy로 가죠, 자동 HTTPS 되니까
[18] 화자4: 나는 nginx가 익숙한데
     ↓
이슈후보 { 질문: "리버스 프록시를 무엇으로 할 것인가", 상태: 쟁점, 근거구간: [17,18] }
```

### 어댑터가 만든 참조는 포트를 넘을 때까지만 산다

구간 번호도 `이슈후보참조`도 **한 추출결과 안에서만 유효한 이름**이다. 저장 경계에서 한 번 해소한다 — 구간 번호는 `(회의록, 순번)`으로, 참조는 후보 ID로. **원시 참조는 DB에 남기지 않는다.**

남기면 조용히 어긋난다. 확인 화면이 후보 하나를 버릴 때, 깨진 제목을 고칠 때, 같은 회의에 두 번째 추출이 돌 때 — 셋 다 이 경계가 이미 하기로 한 일이다. 그리고 실패 모드가 미아가 아니라 **오귀속**이다. 미아는 세면 보이지만 의견이 엉뚱한 이슈에 붙은 것은 아무 데도 안 걸린다. 조용한 절단이 "다 넣었다"로 읽히는 것과 같은 자리다.

### 순서를 나눈다

[mvp-scope.md](./mvp-scope.md)의 두 요구가 충돌하는 것처럼 보인다 — *미확인 후보·쟁점을 추출에 관여시키지 않는다*(관련성 점수를 붙이는 순간 누락이 시작된다)와 *기존 이슈와 연결 제안을 한다.*

순서를 나누면 둘 다 지켜진다.

```
1차 — 회의록만 보고 전량 뽑는다.  기존 이슈 목록 없음  → 누락 방지
2차 — 1차 결과와 기존 이슈를 놓고 겹치는 걸 찾는다     → 연결 제안
```

프롬프트에 기존 이슈 목록을 넣으면 모델이 은연중에 그쪽으로 끌린다. 순서를 나누면 1차가 그 오염에서 자유롭다.

**v0.5는 1차만 만든다.** 연결 자체는 필요하다 — 2회차에 기존 쟁점이 결정되면 추출은 그걸 새 이슈로 뽑으므로, 연결하지 않으면 같은 질문이 회차마다 불어난다. 하지만 **그 연결을 LLM이 할 필요는 없다.** 확인 화면 1장에 기존 쟁점 목록이 나란히 떠 있으면 사람이 눈으로 잇는다.

### 회의록은 쪼개지 않는다

2시간 회의록이 40k 토큰 남짓이라 한 번에 들어간다. 쪼개면 한 이슈가 경계에서 갈라지므로 안 쪼개는 게 품질에 유리하다. 큰 컨텍스트 창의 값은 크기를 다 쓰는 게 아니라 **분할을 고민할 필요를 없애는** 것이다.

### 결과가 여러 벌 쌓인다

추출 품질은 *이 설계 전체가 걸려 있는* 자리다. 관측하려면 같은 회의록에 여러 (프롬프트, 모델) 조합을 돌려 나란히 봐야 한다.

→ 추출 결과에 **프롬프트 해시 + 모델명**이 붙고 **한 회의에** 여러 벌이 병존한다. 회의록이 여러 개여도 합쳐서 한 번 도므로 추출이 붙는 단위는 회의다. 프롬프트는 파일로 둔다 — 코드에 문자열로 박으면 버전이 커밋에 묻혀 결과와 못 잇는다.

**재처리는 이전 벌을 지우지 않는다.** 회의가 *현재 벌*을 가리키고 재처리는 그 포인터를 옮긴다. 지우면 나란히 볼 대상이 사라져 이 절의 목적이 없어지고, 세 벌을 돌려보고 두 번째가 제일 낫다고 판정하는 일이 불가능해진다.

### 표면

```
추출(발화구간[], 프롬프트버전) → 추출결과

[2차 — v0.5에 없음]
연결제안(추출결과, 기존이슈[]) → 연결후보[]
```

메타는 위 `추출결과` 안에 있다. **회의록이 여러 개여도 포트는 발화 구간 목록 하나만 받는다** — 합치는 것은 도메인의 일이고, 구간 번호는 합친 것 기준이다.

추출기는 오디오도 공급자도 모르고, 도메인의 이슈·용어집·상태도 모른다. 아는 건 "발화 구간 목록이 들어오면 구조를 뱉는다"뿐이다.

## ⓷ 녹음 경계 · 재처리

### 쪼개는 이유가 둘이고, 자리가 다르다

| | 왜 | 어디 |
|---|---|---|
| 파일 크기·길이 제한 | 공급자 제약 | **어댑터 안** — 도메인은 "회의 하나 = 파일 하나"로 본다 |
| 논의를 두 덩이로 | 지연 숨기기 | **도메인** — 사람이 누른다 |

헷갈리면 공급자 제약이 도메인으로 샌다.

### 종료 후 일괄 + 어댑터 내부 병렬 청킹

청킹은 제약이면서 **병렬화 기회**다. 긴 오디오를 조각내 동시에 던지면 전체 대기가 가장 긴 조각 하나로 줄어든다. 통으로 던지는 것보다 빠르다.

그래서 회의 중 자동 구간 전사는 만들지 않는다. 아끼는 시간이 몇 분인데 오디오 실시간 분할·업로드와 경계 품질 저하를 짊어져야 한다.

대기가 실제로 길면 **사람이 논의를 두 덩이로 끊는다.** 자동 분할이 아니라 버튼이라 훨씬 단순하다.

→ **스키마는 "회의 하나 = 회의록 여러 개"를 받고, v0.5 화면은 1:1로만 쓴다.** 추출은 어느 쪽이든 회의록 전체를 합쳐 한 번 돈다 — 한 이슈가 전반·후반에 걸칠 수 있다.

### 트리거

**녹음 종료 = 업로드 = 처리 시작.** 자동이다.

서버가 죽어 잡이 유실돼도 오디오가 보존되므로 재처리로 복구된다. 별도 장치를 두지 않는다.

### 재처리와 재추출

**재처리는 1급 기능이다.** [mvp-scope.md](./mvp-scope.md)의 판정 절차가 *1회차 용어집을 확인한 뒤 같은 오디오를 다시 전사해 다시 추출한다* 고 요구하고, 공급자·모델 비교도 같은 오디오를 여러 번 돌리는 일이다.

확인이 끝난 회의를 재처리하는 경우가 있으므로 동작을 명시적으로 나눈다:

| 동작 | 언제 | 무엇이 남나 |
|---|---|---|
| **재처리** | 확인 전 | 이전 결과를 교체한다 |
| **재추출(이슈 버리기)** | 확인 후 | 확인된 이슈를 폐기하고 다시 만든다. **용어집은 남는다** |

두 번째가 1회차 판정 절차의 동작이고, 1회차 답에 박힌 깨진 표기도 이걸로 함께 풀린다 — 재추출 시점에는 용어집이 있어 안 깨진다.

**2회차 이후에 재추출을 쓰고 싶어지면 그게 신호다.**

## 어댑터 세 벌

각 seam 뒤에 어댑터가 세 종류 선다. 셋 다 같은 계약 테스트를 통과해야 한다.

| | STT | 추출 |
|---|---|---|
| **진짜** | CLOVA / gpt-4o-transcribe | LLM |
| **재생** | 녹화된 응답 → 정규화 검증 | 녹화된 응답 → 파싱 검증 |
| **시뮬레이터** | 대본 + 오염 규칙 → 사슬 검증 | 마커 대본 → 결정적 결과 |

셋을 갈아끼울 수 있는 것이 이 seam들의 두 번째 값이다. 교체 가능성과 테스트 가능성이 같은 구조다 ([ADR 0005](./adr/0005-simulate-rounds-not-calls.md)).
