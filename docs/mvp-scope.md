# MVP 범위

## 만드는 것

> 대면 회의를 녹음해 **팀이 답해야 할 질문(이슈)** 을 뽑아내고, 회의 직후 참석자가 그 자리에서 확인하고 결정하는 도구. 기록은 MCP로 AI에게 제공되지만, AI는 결정할 수 없다.

우리 팀(6명)이 곧 사용자다. 인증·멀티테넌시·SaaS 배포는 범위 밖이다.

## 푸는 문제

| | 문제 | 어떻게 |
|---|---|---|
| 1 | 빠른 결정이 사람 머릿속에만 남는다 | 이슈로 뽑아 기록 |
| 2 | 나중에 확인할 서기가 필요한데 인원이 없다 | 녹음 → 자동 추출 |
| 3 | 정리하지 않아 6명이 다르게 이해한다 | **회의 직후 그 자리에서 함께 확인** |
| 4 | AI에 매번 내용을 다시 입력해야 한다 | MCP로 이슈 목록 제공 |

3번은 문서가 아니라 **함께 보는 행위**로 풀린다. 짧은 문장을 6명이 같은 시각에 보는 순간이 이 제품의 가치가 가장 높은 지점이다.

## 세 개의 층

결정마다 되돌리기 비용이 다르므로, 지금 확정할 것과 해보고 정할 것을 분리한다.

| 층 | 내용 | 성격 |
|---|---|---|
| **A. 도메인** | 이슈 모델, 상태, 권한, 어휘 | **지금 확정.** 바꾸면 스키마 전체 |
| **B. 외부 계약** | STT 요건, 미래의 작업관리 도구 | **요건만 확정.** 구현체는 미정 |
| **C. MVP 실행** | 파이프라인, 프롬프트, 화면, 보관 정책 | **해보고 정함.** 싸게 바뀜 |

A는 [CONTEXT.md](../CONTEXT.md)와 [ADR](./adr/), B는 [stt-requirements.md](./stt-requirements.md), C는 이 문서다.

**공급자나 외부 도구가 바뀌어도 A는 무사하다.** 교체 위험은 C에만 있다.

이 구분은 실측으로 얻었다. 설계 도중 실제 녹음 한 번이 결정 둘(**화자 불필요 / 오디오 삭제**)을 뒤집고, 하나(**회의 종료 후 일괄 처리**)는 재검토 끝에 확인해줬다. 뒤집힌 것도 확인된 것도 전부 "해보면 아는 것"이었고, **도메인 모델은 손대지 않았다.**

## v1 — 회의 루프

문제 1·2·3이 여기서 풀린다.

```
녹음 → 전사 → 추출 → 확인 화면 → 저장
```

- **입력:** 대면 회의, 테이블 위 마이크 하나. **화자 분리 포함.** 명시적 시작/종료. 상시 녹음은 하지 않는다
- **처리:** 회의 종료 후 일괄. **실시간 처리 없음**
- **저장:** 작업 repo 밖 팀 공용 클라우드 서버, SQLite
- **보관:** 회의록 보관. **오디오 보존**(잘못된 인식 확인, 중요 내용 상기)

### 추출하는 것

| 대상 | 어디로 간다 |
|---|---|
| **이슈 후보** | 확인을 거쳐 이슈가 된다 |
| **미결정 사유** | 쟁점 상태로 남는 이슈에 붙는다 |
| **의견 + 화자** | 이슈의 근거로 붙는다 |
| **할 일** | 결정에서 도출되어 이슈에 붙는다 |
| **용어 후보** | 용어집으로 (아래 참조) |

**관대하게 뽑는다.** 애매하면 후보로 남긴다. 과잉추출은 사람이 5초에 버리지만 누락은 영원히 모른다.

### 격리해야 하는 두 곳

검증되지 않은 외부 의존이 둘이다. **둘 다 갈아끼울 수 있어야 한다.**

- **추출** — 프롬프트·모델 교체가 스키마를 건드리지 않아야 한다. 이 설계에서 가장 검증이 덜 된 부분이다
- **STT** — 공급자가 미정이다. 인터페이스가 [4개 필수 요건](./stt-requirements.md)을 반영한 모양이어야 한다(컨텍스트를 넣고, 타임스탬프를 받고, 화자 라벨을 받는다)

v1은 이미 검증한 Soniox를 **임시 구현체**로 붙여서 만든다. 채택이 아니라 자리 채우기다.

### 회의 절차 (운영)

1. **시작 라운드** — 각자 *이름 + 지난 회의 이후 한 일*. 화자 매핑과 할 일 완료 판정의 재료를 동시에 만든다
2. **지난 미확인 후보 · 열린 쟁점 표시** — 회수 지점
3. **논의**
4. **정리** — 확인 화면을 함께 본다

### 확인 화면

**함께 읽는 것** — 짧아야 한다. 읽히지 않으면 0이다

- 새 이슈와 그 결정
- **쟁점으로 남는 것 + 미결정 사유**
- 결정에서 도출된 할 일

**그 자리에서 고르는 것**

- 기존 이슈와 연결 제안 — **자동 연결하지 않는다.** 사람이 고른다
- 관련 기존 이슈 노출 — **충돌 판정은 하지 않는다.** 재료만 놓고 판단은 사람이
- **한 일과 매칭된 할 일의 완료 처리**
- **`실행됨` 전이** — 할 일이 다 끝나도 자동으로 넘어가지 않는다. 결정이 실제로 반영됐는지는 사람이 판단한다
- 화자 이름 매핑 (시작 라운드로 자동 추론되지 않았을 때의 폴백)
- 용어집 후보

**접어두는 것**

- 의견 — 상세에만 들어간다. 화자 오류가 매일 보는 화면을 오염시키지 않게 한다

### 용어집 — 사람이 처음부터 쓰지 않는다

용어집은 **서비스를 쓰는 팀의 소유물**이지 우리가 제품에 심어두는 것이 아니다. 그런데 팀에게 "쓰세요"라고 요구하면 안 쓴다. 컨텍스트를 손으로 채우는 번거로움이야말로 이 제품이 없애려는 것이기 때문이다.

**첫 회의 자체를 용어 수집 기회로 쓴다.**

```
1회차   컨텍스트 없이 전사  →  용어가 깨짐
        깨진 후보를 추출    →  "이 단어들, 뭔가요?"
        사람이 고침         →  용어집 생성
2회차~  자동 적용
```

이슈 추출과 같은 패턴이다 — **관대하게 뽑고, 후보로 놓고, 사람이 확인한다.** 반복 등장하는 미확인 고유명사는 기계적으로 뽑을 수 있고 사람은 O/X만 한다.

## v2 — MCP

문제 4가 여기서 풀린다. 로그가 비어 있으면 가치가 0이므로 v1 뒤에 온다.

| 도구 | 비고 |
|---|---|
| 이슈 목록 | **전량, 한 줄씩.** 질문 + 상태 + 답. 200건이 약 5,000토큰 |
| 미확인 후보 목록 | **미확인 표시를 달고** 나간다. 정보를 버리지 않되 신뢰 등급을 구분한다 |
| 이슈 상세 | 근거, 의견, 할 일, 이력 |
| 회의록 구간 | 원문. 거의 쓰이지 않는다 |
| 후보 생성 | 허용 |
| 재열기 | 허용 |
| ~~결정~~ | **제공하지 않는다** ([ADR 0002](./adr/0002-ai-cannot-decide-issues.md)) |

**검색형이 아니라 전량 목록인 이유:** AI는 자기가 뭘 모르는지 모른다. "결제 붙여줘"를 받은 AI는 "환불 정책" 이슈를 검색할 생각조차 못 한다. 목록을 전량 주면 발견이 가능해진다.

**시간으로 자르지 않는다.** 결정은 오래됐다고 죽지 않는다. 목록에서 빠지는 유일한 조건은 무효 상태다.

**호출은 수동이다.** 훅으로 자동 주입하지 않는다. 대신 **도구 설명(description)에 공을 들인다** — AI가 언제 부를지 판단하는 유일한 근거이고, 훅과 달리 클라이언트에 종속되지 않는다.

## 하지 않는 것

| | 이유 |
|---|---|
| 실시간 전사·실시간 개입 | 회의 속도를 공격한다. 화자 분리 정확도도 떨어진다 |
| AI의 충돌 판정 | 오탐 한 번에 신뢰를 잃는다. 노출까지만 |
| 이슈 계층(주제 > 이슈) | 트리는 한 번 틀리면 그 가지가 통째로 안 보인다. 평평하게 두고 검색 |
| 미분류 통 | 반드시 쓰레기통이 된다. 후보 상태가 그 자리를 대신한다 |
| 회의 밖에서 할 일 편집 | 그 순간 작업 공간이 된다 ([ADR 0003](./adr/0003-no-external-task-tool.md)) |
| 상시 녹음 | 오디오 보존으로 얻은 신뢰를 그 자리에서 반납하는 일 |
| **사실·의견을 독립 레코드로 두는 것** | 의견은 **이슈에 붙어서** 기록되지 화자별 목록으로 따로 서지 않는다. 사실은 근거로 흡수된다. 추적 대상은 이슈뿐이다 |

## 열려 있는 것

**검증해야 할 것 — 이 설계 전체가 여기 걸려 있다.**

| | 확인 방법 |
|---|---|
| **추출 품질** — 한국어 6인 대면 회의록에서 이슈를 쓸만하게 뽑는가 | v1이 도는 첫날. 6명이 결과를 함께 보고 판정 |
| **이슈 과잉 분할** — 3개가 아니라 15개로 쪼개지는가 | 같은 날. 그렇다면 입도 기준을 재설계 |
| **질문 합성의 어색함** — "그냥 이렇게 하죠"에서 질문을 역산할 수 있는가 | 같은 날. 실패하면 이슈 모델 자체를 재검토 |
| **확인 화면이 길어지는 문제** | 이슈 필드가 늘면서 *"짧아서 읽힌다"* 는 전제가 약해졌다. 첫 회의에서 실제로 몇 줄이 되는지 재고, 넘치면 접는 범위를 넓힌다 |

**실측 후 확정할 것**

- `실행됨` 상태를 실제로 쓰는가, 아니면 할 일 완료로 충분한가
- 미확인 후보가 회수되지 않고 누적되는 속도
- **용어집 후보 추출이 쓸만한가** — 깨진 회의록에서 원래 단어를 사람이 알아볼 수 있는 형태로 뽑히는지
- **컨텍스트 한도가 찰 때의 우선순위** — 용어집 vs 이슈 목록
- 오디오 보관 기간
- STT 공급자 ([요건](./stt-requirements.md))
- 서버 위치(클라우드 가정) 및 LLM 선택

**의도적으로 답하지 않은 것**

- 미래의 작업관리 도구 연동 — 어떻게 불편할지 알 수 없으므로 지금 맞추지 않는다
