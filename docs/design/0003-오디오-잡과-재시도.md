# 설계 합의 — 오디오를 올리면 잡이 돌고, 실패하면 다시 돌린다

대상: [decision-log/decision-log#3](https://github.com/decision-log/decision-log/issues/3)
선행: #2 걷는 뼈대 (닫힘). 그릴링 세션에서 합의된 내용이며, 용어는 루트 `CONTEXT.md`를 따른다.

## 자리

- **잡 실행기가 부르는 `처리` 인터페이스를 새로 둔다.** 이 티켓은 잠깐 돌다 완료로 끝나는 가짜를 꽂고, 뒤 티켓(진짜 전사·추출)이 이 자리에 `회차오케스트레이터.돈다()`를 부르는 구현을 꽂는다. 기존 자리 재활용(가짜 어댑터로 `돈다()` 실행)은 하지 않는다 — 티켓이 "가짜 = 잠깐 돌다 완료"라고 명시했고, 이 티켓의 산출물은 처리 내용이 아니라 잡의 생명주기다.
- **미룬 충돌**: 현재 `돈다()`는 회의를 자기가 만든다(`회의들.새회의()`). 이 티켓은 사람이 회의를 먼저 만들므로, 진짜 연결 티켓에서 `돈다()`가 회의ID를 받도록 고쳐야 한다. **이 티켓에서 풀지 않는다.**

## 거처

- **잡 기계장치는 전부 `app`에 산다** — 잡 테이블 접근, 스레드풀, 상태 전이, `처리` 인터페이스. 도메인과 CONTEXT.md는 건드리지 않는다.
- 근거: CONTEXT.md의 추적 대상("이슈와 할 일")에 잡이 없다. 처리가 동기가 되는 순간 증발하는 어휘는 도구의 말이지 팀의 말이 아니다. `sim`도 잡 없이 동기로 회차를 돈다.

## 잡 모델

- **오디오 업로드 하나 = 잡 하나.** 회의당 잡 유니크. 잡이 처리 전체를 덮는다. 단계별 절약(전사 성공 후 추출만 실패)은 뒤 티켓의 처리 구현이 "회의록이 이미 있으면 전사를 건너뛴다"로 자리 안쪽에서 해결한다.
- **진행률은 처리 구현이 임의의 분수로 보고한다.** `진행(완료, 전체)` 콜백 하나. 잡 테이블엔 정수 두 칸. 단계 이름은 고정하지 않는다 — 진짜의 단계 구조는 뒤 티켓이 정한다.
- **재시도는 같은 행 리셋.** `상태='실패'`인 행만 대기중으로 되돌리는 조건부 UPDATE — 0행이면 거절(처리중 재시도 경쟁 차단). 시도 이력은 남기지 않는다. 실패의 법의학은 애플리케이션 로그의 일이다.
- **부팅 쓸어담기.** 애플리케이션이 뜰 때 대기중·처리중으로 남은 잡을 전부 실패("애플리케이션 재시작으로 중단됨")로 바꾼다. 자동 재개는 없다 — 잡이 앱을 죽인 원인이면 자동 재개는 죽음의 반복이다. 수용 기준도 "다시 돌릴 수 있다"(수동)까지만 요구한다.
- **투입은 직접 제출.** 업로드 핸들러가 잡 행을 대기중으로 넣고 그 자리에서 스레드풀에 제출한다. 폴링 루프 없음 — 부팅 쓸어담기 덕에 재개할 잡이 없다. 스레드풀은 고정 크기(기본 2, 설정으로 조정).
- **부팅 쓸어담기는 요청을 받기 전에 끝난다.** 빈 초기화(`@PostConstruct`) 시점에 돌므로 웹 서버가 커넥션을 열기 전에 완료되는 것이 배선으로 보장된다. 구현 전 모델 검사에서, 쓸어담기가 요청 수신과 인터리빙되면 처리중인 잡을 실패로 오판해 재시도 거절을 뚫고 같은 잡의 동시 처리와 완료 뒤집힘이라는 반례를 만들었다 — 그래서 `ApplicationRunner`는 쓰지 않는다.

## 명단과 참가자

- **명단은 #6이 이미 만들어 둔 것을 그대로 쓴다.** 이 합의를 쓸 때는 #3이 #6보다 먼저 갈 예정이라 "`participant` 테이블은 이 티켓이 만들고, `명단저장소` 포트 없이 app에서 jOOQ로 직접 읽는다"였다. **구현 시점에는 #6이 먼저 들어와** 테이블(`V2__participant.sql`)도 `명단저장소` 포트도 `GET /api/participants`도 이미 있었으므로, 이 티켓은 셋 다 재사용하고 아무것도 새로 만들지 않는다. 시드는 여전히 없다 — 명단은 #6의 설정 화면에서 팀이 넣는다.
- **회의 참가자는 스냅샷이다 — FK를 걸지 않는다.** 생성 시 명단을 읽어 전체 선택된 기본값으로 보여주고, 선택된 이름들을 `meeting_participant`에 복사한다. 근거: #6 합의가 "통째 교체·이름 고치기 자유"를 "명단을 참조하는 게 없다"는 전제로 허용했다 — FK를 걸면 그 합의를 소급해서 깨뜨린다. 명단이 나중에 바뀌어도 그 회의에 그 사람들이 있었다는 사실은 안 변한다.
- 명단이 비어 있으면 참가자 기본값도 빈 목록이다. 기본값 기제는 통합 테스트에서 행을 넣어 검증한다.

## 스키마

```sql
alter table meeting
    add column title      text not null,
    add column held_on    date not null,   -- 사용자가 고르는 회의 날짜, 기본 오늘
    add column audio_path text;            -- 회의당 오디오 하나

-- participant 는 #6 이 이미 만들었다(V2) — 이 티켓의 마이그레이션(V3)에는 없다.
-- create table participant (name text primary key);

create table meeting_participant (       -- 스냅샷 복사, FK 없음 (participant 쪽)
    meeting_id uuid not null references meeting(id),
    name       text not null,
    primary key (meeting_id, name)
);

create table job (
    id             uuid primary key,
    meeting_id     uuid not null unique references meeting(id),
    state          text not null,        -- 대기중 · 처리중 · 완료 · 실패
    progress_done  int  not null default 0,
    progress_total int  not null default 0,
    failure_reason text,
    created_at     timestamptz not null default now(),
    updated_at     timestamptz not null default now()
);
```

상태값은 한글 텍스트 — `issue_candidate.state`가 도메인 enum을 한글로 담는 기존 관례를 따른다.

## 오디오 저장

- `{데이터디렉토리}/{회의ID}/{원본파일명}`에 두고 경로만 `meeting.audio_path`에 저장한다.
- 데이터 디렉토리는 설정 프로퍼티. compose에 볼륨을 물려 강제종료 후에도 파일이 남는다.
- `audio_path`가 이미 있으면 업로드 거절 — 재업로드(교체)는 범위 밖, 실패는 재시도로 푼다.

## 가짜 처리

- 5단계 × 1초로 돌며 단계마다 `진행(완료, 전체)`을 보고하고 완료로 끝난다.
- **파일명에 `fail`이 들어가면 항상 실패한다** — 결정적이라 테스트와 시연이 쉽다. 실패 사유에 가짜임이 드러나는 문구를 담는다.
- "재시도가 완료로 끝나는" 시연은 강제종료 시나리오가 맡는다: 정상 파일 처리중에 죽였다 살리면 부팅 쓸어담기로 실패가 되고, 재시도하면 완료로 끝난다. fail-once 같은 상태 있는 가짜는 만들지 않는다.

## API와 화면

- REST 다섯 개: 회의 생성(제목·날짜·참가자) / 회의 목록 / 회의 단건 조회(잡 상태 포함) / 오디오 업로드(multipart, 업로드가 곧 처리 시작) / 재시도.
- 화면은 한 장: 회의 목록 + 생성 폼, 회의를 고르면 같은 페이지에 상세(업로드 · 상태 · 재시도). 라우터는 깔지 않는다 — #6 합의("화면 라우팅은 화면 이슈 #9·#10에서 정한다")를 존중한다.
- 폴링 2초, 잡이 대기중·처리중일 때만.

## 테스트

- 통합: 회의 생성 → 업로드 → 폴링으로 완료 도달. `fail` 파일명 → 실패와 사유 → 재시도 → 다시 실패(같은 파일이므로). 부팅 쓸어담기: 처리중 행을 심고 띄우면 실패로 바뀐다. 처리중 재시도 거절.
- 참가자 기본값: 명단 행을 넣고 생성 시 전체가 기본값인지.
- 화면 테스트 1개: 업로드 → 상태 갱신 → 실패 → 재시도 흐름.

## 이 이슈에서 안 하는 것

이슈 수용 기준 그대로 — 진짜 전사·추출, 큐 미들웨어, 인증·사용자 식별. 추가로: 재업로드(오디오 교체), 잡 시도 이력, 단계 이름 표시, 자동 재개, 화면 라우팅, `명단저장소` 포트와 설정 화면(#6), `돈다()`의 회의 생성 충돌 해소(진짜 연결 티켓).
