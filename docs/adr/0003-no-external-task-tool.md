# 외부 작업관리 도구를 가정하지 않으며, 도입하더라도 과거를 옮기지 않는다

노션·Jira 등 외부 작업관리 도구가 없다고 가정하고 설계한다. 할 일은 우리가 상태를 갖고 추적하며, 회의 시작의 "한 일" 보고와 맞물려 처리 여부를 판정한다.

아직 도입하지 않은 시스템의 모양(노션인지 Jira인지, 어떤 스키마인지)은 추측일 수밖에 없고, 그 추측에 맞춘 연동 코드는 검증할 방법조차 없다.

## 이 결정을 안전하게 만드는 조건

**나중에 외부 도구가 들어와도 과거 할 일을 옮기지 않는다.** 경계일 이후의 할 일만 그쪽에서 생기게 한다.

할 일은 수명이 짧아 과거의 것은 이미 끝났거나 죽었다. 옮기지 않으면 입도 불일치도, 두 시스템이 어긋나는 문제도 발생하지 않는다. 반대로 성실하게 마이그레이션하려 들면 비용을 다 치른다. 수명이 긴 이슈는 애초에 외부 작업관리 도구가 다루는 대상이 아니므로 계속 우리 것으로 남는다.

이 조건을 적어두지 않으면 나중에 누군가 선의로 전체 이전을 시도한다. **그 시점이 이 결정이 비싸지는 유일한 지점이다.**

## 도입 시점을 알려주는 신호

**회의 밖에서 할 일을 손대고 싶어지는 순간**(재배정, 기한 조정, 우선순위 정렬)이 외부 도구가 필요한 순간이다. 그 전까지는 우리 도구로 충분하며, 그 욕구가 끝내 생기지 않는다면 외부 도구는 필요 없어진 것이다.

이 신호는 스코프 팽창을 막는 장치이기도 하다. 외부 도구가 없다고 가정하면 그 빈자리를 채우려는 압력(담당자 관리, 기한 알림, 필터)이 생기는데, 위 선을 넘는 순간 우리는 작업관리 도구를 만들고 있는 것이다.

## 이 결정이 뒤집히는 경우

- 외부 도구 도입이 이미 확정됐고 시점이 가까울 때 — 추측이 아니라 알려진 대상이므로 맞춰 설계하는 게 맞다
- 팀이 이미 다른 도구에서 할 일을 관리하고 있을 때 — 이 경우 우리가 할 일 상태를 갖는 것 자체가 처음부터 실수다
